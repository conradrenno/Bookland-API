## Commands

```bash
# Build all modules
./mvnw clean install

# Build skipping tests
./mvnw clean install -DskipTests

# Run the application (dev profile with H2) — start the brokers first, then the five processes:
# the gateway (port 8080) is where clients call; it routes to the API (8083) and the catalog service
# (8082, gRPC 9091); the identity service (9000) issues the tokens both validate; the notification
# service (no port) emails the customer through RabbitMQ and Mailpit
docker compose up -d kafka redpanda-console rabbitmq mailpit
./mvnw spring-boot:run -pl bookland-identity-app
./mvnw spring-boot:run -pl bookland-catalog-app
./mvnw spring-boot:run -pl bookland-app
./mvnw spring-boot:run -pl bookland-gateway
./mvnw spring-boot:run -pl bookland-notification-app

# Run all tests
./mvnw test

# Run tests for a single module
./mvnw test -pl bookland-user

# Run a single test class
./mvnw test -pl bookland-user -Dtest=UserDomainServiceTest

# Run with Docker (prod profile, PostgreSQL + Flyway): gateway on 8080 (API 8083, catalog 8082), identity on 9000
docker compose up --build

# Start from an empty database (wipes the pgdata and covers volumes)
docker compose down -v && docker compose up --build
```

Each application has its own Dockerfile (`bookland-app`, `bookland-identity-app`, `bookland-catalog-app`, `bookland-gateway`, `bookland-notification-app`). Each copies **every** module's `pom.xml` — the parent lists them all and the reactor refuses to start with one missing — but only the `src` of the modules that image builds, to keep the dependency-download layer cacheable. **Those lists duplicate `pom.xml` and nothing enforces them** — a new module must be added to **every** Dockerfile's pom list, or those image builds fail. The compose Postgres runs `docker/postgres/initdb` (shell scripts there must stay LF — `.gitattributes` pins `*.sh`) only on an empty volume: it gives each service **a role of its own** (`APP_DB_USER`, `IDENTITY_DB_USER`, `CATALOG_DB_USER`, `NOTIFICATION_DB_USER`) that owns its database and has no `CONNECT` on the others'. A database added later does not reach an existing volume: create its role and database by hand with the script's statements, or `down -v`. **No service connects as `POSTGRES_USER`** — the image makes it a superuser, which reads every database. `.dockerignore` keeps `target/`, `.git`, `bookland-data/` and `.env` out of the build context.

**Dev endpoints:**
- **Gateway — the address clients use**: `http://localhost:8080`. Spring Cloud Gateway (Server WebMVC, `bookland-gateway`), routes only: `/api/v1/books/*/reviews[/**]` → API; `/api/v1/books[/**]`, `/api/v1/categories[/**]`, `/api/v1/inventory/**`, `/media/**` → catalog; the rest of `/api/v1/**` → API. **The routes are tried in list order** and the reviews route must stay above the catalog's (measured: swapped, the review requests went to the catalog) — `GatewayRoutingTest` pins every path against two stub servers. No token validation (every service is a resource server), no Swagger, no `/error`; the identity service is not routed (the issuer keeps its address). **Timeouts are explicit** — `spring.http.clients.connect-timeout`/`read-timeout` (Boot's HTTP client settings, which the gateway uses), 2 s / 10 s, env `GATEWAY_CONNECT_TIMEOUT`/`GATEWAY_READ_TIMEOUT`: they have no default, and a stopped or frozen service held requests for as long as the caller waited (measured in 5d). `UpstreamFailureResolver` (a `HandlerExceptionResolver`, since the routes are functional endpoints that `@ExceptionHandler` does not reach) renders a timeout as **504 `UPSTREAM_TIMEOUT`** and an I/O failure as **502 `UPSTREAM_UNAVAILABLE`**, problem+json, instead of Boot's code-less 500 — written as UTF-8 bytes, since the servlet writer appended ISO-8859-1. Pinned by `GatewayTimeoutTest`
- API (the monolith, directly): `http://localhost:8083` — its Swagger UI lives here, not behind the gateway
- Identity service (login, tokens, register, users): `http://127.0.0.1:9000` — the dev issuer
- Catalog service (books, categories, inventory, covers): `http://127.0.0.1:8082`, Swagger at `http://127.0.0.1:8082/swagger-ui.html` (its redirect URI and origin are registered in the identity service's dev config); gRPC `BookCatalog` on 9091. Clients reach it through the gateway; 8082 directly serves its Swagger UI
- Swagger UI: `http://127.0.0.1:8083/swagger-ui.html` (API), `http://127.0.0.1:8082/swagger-ui.html` (catalog) and `http://127.0.0.1:9000/swagger-ui.html` (identity) — **127.0.0.1, not localhost**, for the Authorize button: the redirect URIs must be the loopback IP (RFC 8252). The API's UI exchanges the code with a `fetch` to `127.0.0.1:9000/oauth2/token`, another origin, which the identity service allows through CORS (`bookland.oauth2.cors-allowed-origins`, token endpoint only)
- H2 Console: `http://localhost:8083/h2-console` (JDBC URL: `jdbc:h2:mem:booklanddb`), `http://localhost:9000/h2-console` (`jdbc:h2:mem:identitydb`) and `http://localhost:8082/h2-console` (`jdbc:h2:mem:catalogdb`)
- Redpanda Console (topics, messages, consumer offsets): `http://localhost:8081` — a UI only; the broker is Apache Kafka (KRaft, single node), reachable at `localhost:9092` from the host and `kafka:29092` inside the compose network
- RabbitMQ management (queues, messages, consumers): `http://localhost:15672` (user `bookland`/`bookland` unless `RABBITMQ_USER`/`RABBITMQ_PASSWORD`); AMQP on `localhost:5672`
- Mailpit (every email the notification service sends, none delivered): `http://localhost:8025`; SMTP on `localhost:1025`

## Git Conventions

All commits must follow **[Conventional Commits](https://www.conventionalcommits.org/)**:

```
<type>[optional scope]: <short description>

[optional body]

[optional footer(s)]
```

| Type | When to use |
|---|---|
| `feat` | New feature or endpoint |
| `fix` | Bug fix |
| `refactor` | Code change that is neither a fix nor a feature |
| `test` | Adding or updating tests |
| `docs` | Documentation only |
| `build` | Build system or dependency changes (pom.xml, Docker) |
| `chore` | Miscellaneous maintenance (no production code change) |
| `ci` | CI/CD configuration |

**Scope** is optional and should be the domain module name when relevant (e.g., `feat(user)`, `fix(auth)`, `build(catalog)`).

**Breaking changes** must be marked with `!` after the type/scope (`feat(auth)!:`) and explained in the footer with `BREAKING CHANGE:`.

## Architecture

### Module Structure

```
bookland/               ← Parent POM (dependency management)
├── bookland-gateway/   ← the single entry point (port 8080): routes only, no domain module
├── bookland-app/       ← ASSEMBLY: the monolith (API, port 8083) — orders, payments, reviews, wishlist
├── bookland-identity-app/ ← ASSEMBLY: the identity service (port 9000) — user + auth, its own database; issues the tokens
├── bookland-catalog-app/  ← ASSEMBLY: the catalog service (port 8082, gRPC 9091) — catalog + inventory, its own database
├── bookland-notification-app/ ← ASSEMBLY: the notification service (no HTTP) — notification, its own database
├── bookland-web-support/ ← LIBRARY (platform): HTTP error-contract glue + Bearer-token validation (see below)
└── bookland-{domain}/  ← LIBRARY (domain): one module per domain (user, auth, catalog, orders, reviews, inventory, wishlist, payments, notification)
```

**Assembly modules vs libraries.** A service is an *assembly module* (main class, `application.yml`, migrations, integration tests, Dockerfile — no business logic) plus the *domain libraries* it includes. user and auth are still two separate modules; the identity service runs both in one process and one database, auth reaching user in memory through its ports. The wiring is **by convention, never by name**: the assembly's `pom.xml` puts the jars on the classpath and its `@SpringBootApplication` class sits in the root package `com.devrenno.bookland`, so component/entity/repository scanning and `@ConfigurationPropertiesScan` cover every module's subpackage. Moving a main class into a subpackage silently drops every module from its process. Extracting another service means a new `bookland-<service>-app` and removing those modules from `bookland-app`.

`bookland-web-support` is **not** a shared kernel — the "duplicate it per module" rule (PageQuery, PageResult) still holds for anything with domain meaning. It holds framework glue only: `ProblemDetails`, `ProblemDetailWriter`, `AuthErrorCode`, `RestAuthenticationEntryPoint`, `RestAccessDeniedHandler`, `ValidationExceptionHandler`, `ValidationConfig`, `ErrorResponsesCustomizer`, `AuthenticatedUser` + `AuthenticatedUserArgumentResolver` + `AuthenticatedUserConfig`, and the **resource-server half of security**: `ResourceServerConfig` (the `JwtDecoder` bean with its four validators, the entry point and access-denied beans, and the static `jwtAuthenticationConverter()`), `ResourceServerProperties` (`bookland.resource-server.*`), `ApiAudienceValidator`, `AccessTokenExpiryValidator`, `BearerTokenErrorClassifier`. It must never contain a domain type or depend on another `bookland-*` module, and only `*.infrastructure` packages may import it. It exists so the HTTP error contract — and the ability to validate a token — survive a future split into separate services: a service validates tokens with this module alone, without depending on `bookland-auth` (which holds the private key).

**The `JwtDecoder` reads the public keys from one of two places**: `bookland.resource-server.jwk-set-uri` when set (a service in its own process, over HTTP), otherwise the `JWKSource` bean in the same process, copied as a public-only set. The identity service leaves the URI unset (it hosts the Authorization Server, whose `JWKSource` is that bean); the monolith sets it to the identity service's `/oauth2/jwks`. **The monolith's integration tests blank it again** (`@BooklandIntegrationTest`) and supply a `JWKSource` from `TestSigningKey`, a key generated per context: MockMvc opens no port and no identity service runs, so a decoder fetching the JWKS over HTTP would fail every test. `TestAccessTokens` must keep writing the claims the identity service issues — pinned on that side by its `AuthorizationCodeFlowIntegrationTest`. An unreachable JWKS answers **500**, not 401: the token is not at fault. **`jwtAuthenticationConverter()` must stay a static factory, not a `@Bean`**: `JwtConfigurer` looks a `JwtAuthenticationConverter` bean up for every chain that does not set one (checked in its bytecode), so a bean would change the authorities on the Authorization Server's own chain too.

**All error responses follow `docs/error-contract.md`** — `application/problem+json` with a machine-readable `code`, messages in **English**. Bean validation is handled by the **single** `ValidationExceptionHandler` in `bookland-web-support` (`@Order(HIGHEST_PRECEDENCE)`), which emits an `errors` map (field → messages) so a client can render errors inline; **a module must never add its own `MethodArgumentNotValidException` handler** — two advices for the same exception leaves the winner up to bean ordering and the payload shape drifts per module. Module advices keep owning their business exceptions (404/409/422) and build them through `ProblemDetails.of(status, detail, code)` — every error response in the API carries a `code`, and the table of business codes is in `docs/error-contract.md`. Note that **not every 403 means "wrong role"**: `ORDER_ACCESS_DENIED` and `PURCHASE_REQUIRED` are business 403s, only `INSUFFICIENT_ROLE` is about authorities. `ValidationConfig` pins constraint messages to English: Hibernate Validator otherwise resolves them against the host JVM's default locale, so the same build answered Portuguese on a pt-BR developer machine and English in the container. `OpenApiConfig` (bookland-web-support, so every process publishes the same contract; title from `bookland.openapi.title`, login URLs from `bookland.resource-server.issuer`) publishes the contract in `/api-docs` — `ProblemDetail`/`ValidationProblemDetail` schemas, a `default` error response on every operation, an explicit `400` wherever a request has input, and the `bearerAuth` scheme. Per-operation 401/403/404/409 are deliberately **not** enumerated (they depend on `ApiSecurityConfig` and on domain exceptions no annotation declares, so a hand-kept list goes stale silently). **Every request-DTO `String` bound to a `varchar(n)` column needs `@Size(max = n)`.** Nothing enforces this — Hibernate does not validate length before the insert, so a missing bound turns a bad request into a `DataIntegrityViolationException`, i.e. a 500 where a 400 naming the field belongs. Fields backed by `text` (`books.synopsis`, `reviews.comment`) are deliberately unbounded. Note `books.cover_image_url` and `order_items.cover_image_url` are both `varchar(255)`: raising the DTO bound without migrating **both** columns just moves the 500 to checkout.

**A handler answering anything other than 200 must carry `@ResponseStatus`** (e.g. `@ResponseStatus(HttpStatus.CREATED)` next to `ResponseEntity.status(HttpStatus.CREATED)`): springdoc infers 200 from the return type and cannot see through `ResponseEntity.status(...)`, so without it the published document claims 200 and every generated client gets the wrong success type. The annotation is redundant at runtime — `ResponseEntity` wins — and exists to keep the document honest. The current cases are pinned in each application's `OpenApiErrorContractIntegrationTest`, and **`WebLayerRulesTest`** (ArchUnit, in each application — the only places with their modules on one classpath) fails the build on a handler in `..infrastructure.web..` that calls `ResponseEntity.status/created/noContent/accepted` without `@ResponseStatus`.

`bookland-app` and `bookland-identity-app` have no business logic — each exists solely to assemble its domain modules and host its `application.yml`. The `spring-boot-maven-plugin` runs only in those two.

### Layered Package Layout (per domain) — 4-layer Clean Architecture

Each domain module follows **four** layers. **Domain, Application and Adapters are framework-free** (Lombok is allowed — it is source-only and leaves no bytecode trace). Only **Infrastructure** may touch Spring / JPA / Jackson. Dependencies always point inward: `infrastructure → adapters → application → domain`.

> All 8 domain modules follow this model (migration from the previous 3-layer `@UseCase` + `api/` layout completed in July 2026). `bookland-user` is the reference implementation — follow its shape for all new code.

```
com.devrenno.bookland.{domain}/
├── domain/                 [framework-free]
│   ├── entity/             ← Pure Java; static factories (create/reconstitute) encapsulate intrinsic invariants; private ctor, no public setters
│   ├── valueobject/        ← Immutable value types (e.g. Email, UserId)
│   ├── service/            ← Domain rules needing cross-aggregate/lookup data (e.g. email uniqueness); no I/O, no Spring
│   └── exception/          ← Domain-specific exceptions
├── application/            [framework-free]
│   ├── service/            ← *Service: implements port/in; RETURNS DOMAIN ENTITIES; private ctor + static create(...) factory (no @UseCase)
│   ├── dto/                ← Input commands + query read-models (no output DTOs — use cases return entities or read-models)
│   ├── common/             ← PageQuery / PageResult (framework-free pagination, duplicated per module)
│   └── port/
│       ├── in/             ← Use-case interfaces (e.g. RegisterUserUseCase) — return domain entities
│       └── out/            ← Outbound ports (UserPersistencePort, PasswordEncoderPort, TransactionPort)
├── adapters/               [framework-free]
│   ├── controller/         ← Internal controller: orchestrates use cases + presenter; also the module's composition root (static create(ports) wires the inner graph)
│   ├── presenter/          ← Plain-Java presenters: domain entity → ViewModel
│   └── viewmodel/          ← Output DTOs (no Jackson); delivered as-is by the HTTP layer
└── infrastructure/         [Spring]
    ├── web/                ← @RestController (delegates to internal controller), request DTOs, request mappers (MapStruct), @RestControllerAdvice
    ├── config/             ← Composition root beans: 1 @Bean per module entry point calling *Controller.create(ports) + cross-module use-case beans
    ├── persistence/        ← JPA entities, Spring Data repos, adapters implementing out-ports, persistence mappers (JPA entity ⇄ domain via reconstitute)
    ├── adapter/            ← Cross-module adapters: implement this module's out-ports by calling other modules' in-port beans (or the reverse — e.g. orders implements catalog's ActiveOrderCheckPort)
    ├── transaction/        ← TransactionAdapter (TransactionTemplate) implementing TransactionPort, where the module needs it
    ├── messaging/          ← Kafka: producers implementing out-ports, @KafkaListener inbound adapters (the messaging twin of @RestController), the module's topics and listener container factory
    └── security/           ← JWT filter, BCrypt adapter (user/auth modules)
```

### Key Design Rules

**Framework-free inner layers, enforced by ArchUnit.** Domain, Application and Adapters must not depend on `org.springframework..`, `jakarta.persistence..` or `com.fasterxml.jackson..`. Each module has an `ArchitectureRulesTest` (see `bookland-user`) that fails the build on violation, plus a `layeredArchitecture` rule enforcing the inward dependency direction. There is **no `@UseCase` annotation** — services are plain Java.

**Two controllers, two roles:**
- **Internal controller** (`adapters/controller`) — plain Java. Orchestrates `port/in` use cases and calls the Presenter to produce a `ViewModel`. Is also the module's **composition root**: its static `create(...)` factory receives the outbound ports (as interfaces) and manually wires the domain service + use cases + presenter.
- **API controller** (`infrastructure/web`, `@RestController`) — HTTP adapter only. Maps HTTP → internal controller call → `ResponseEntity<ViewModel>`. Depends only on the internal controller, never on `*Service`.

**Use cases return domain entities**, not DTOs. Output shaping happens in the Presenter (→ ViewModel). Cross-module consumers depend on the source module's `port/in` and receive its **domain entities** (e.g. `bookland-auth` maps the `User` entity from `GetUserByEmailUseCase`/`RegisterUserUseCase` into its own `AuthUserDto`).

**Exception — use cases whose output needs data from another module return a query read-model** from `application/dto/` instead of the entity, assembled in the application layer from the aggregate + an out-port lookup (`CartView`/`CartItemView` via `BookInfoPort`, `WishlistView` via `WishlistBookInfoPort`, `LowStockBook` via `LowStockBooksPort`). The assemblers (`CartViewAssembler`, `WishlistViewAssembler`) are package-private in `application/service/` and **degrade gracefully** when the lookup finds nothing — a cart/wishlist item whose book left the catalog renders as `"Unavailable"`/`available: false` rather than failing the whole response. `ReviewView` is no longer one of these: the author's name is **stored on the review** (`reviews.customer_name`), taken at creation from the caller's access token (the `name` claim, via `AuthenticatedUser.name()`), so neither creating nor listing a review asks the user module anything — reviews has no dependency on `bookland-user` at all. The name is frozen at review time by design.

**Manual wiring (composition root), no `@UseCase`/`@Service` on inner classes.** Infrastructure creates only the outbound-port adapters (`@Repository`/`@Component`) and exposes **one `@Bean`** per module entry point that calls `*Controller.create(ports)`. Inner classes are never Spring beans and never self-annotate. Never instantiate an infrastructure adapter from inside an inner layer.

**Cross-module use cases must be explicit `@Bean`s.** A use case consumed by another module (e.g. orders' `VerifyPurchaseUseCase` → reviews, `AddCartItemUseCase` → wishlist) must be exposed as its own `@Bean` in the module's `*BeansConfig` — forgetting one fails context startup in the consumer's adapter.

**Events between modules go through Kafka, and the contract is the JSON, not a class.** The first one is `BookRatingChanged` (reviews → catalog, topic `bookland.reviews.book-rating-changed`): reviews no longer calls `UpdateBookAverageRatingUseCase`, it publishes through `BookRatingEventPort` and catalog's `BookRatingChangedListener` applies it, so the rating lands a moment after the review request returns. The rules: the **producer owns the topic** (`NewTopic` in its `infrastructure/messaging`) and the consumer **duplicates the topic name** rather than importing it; **only the owner creates it**: every application sets `spring.kafka.consumer.properties.allow.auto.create.topics: false`, because with the client's default a consumer that starts first creates the topic with the broker's 1 partition — the owner's `NewTopic` then raises it to 3 while that consumer keeps reading partition 0 alone until its next metadata refresh (seen in 6b, notification started before the monolith); each side has its **own record** for the payload, and the consumer ignores unknown fields; the value is a **JSON string written with `JsonMapper`**, never Spring Kafka's JSON serializer, which puts the producer's class name in a `__TypeId__` header; the **key is the aggregate id** (here the book id), which is what keeps one aggregate's events in order; the payload carries the **resulting state, not a delta**, so a redelivery is harmless. A consuming module declares its **own listener container factory** with its error policy (`CatalogKafkaConfig`) — never a global `CommonErrorHandler` bean, which would reach every module's listeners, and a second one would make Boot apply neither. **A message a listener cannot apply is never dropped**: after the retries (or at once, for the exceptions marked not-retryable) the factory's `DeadLetterPublishingRecoverer` writes it to `<topic>.<consuming module>.DLT` — one per consumed topic, owned by the consumer (`NewTopic` beans prefixed with the module, since catalog and payments both consume `order-events`), same partition count as the source, `kafka_dlt-*` headers with the group and the cause. Nothing reprocesses them automatically. Pinned by `PaymentSafetyIntegrationTest`. **Events leave through a transactional outbox, never straight to Kafka.** `OutboxBookRatingEventAdapter` implements the port by inserting into `reviews_outbox` **in the caller's transaction** (`Propagation.MANDATORY` — called outside one it throws rather than committing the row alone), so `CreateReviewService`/`ModerateReviewService` wrap the review write and the publish in one `TransactionPort.inTransaction`, and the review and its event commit together or not at all. `ReviewsOutboxRelay` (`@Scheduled`, every second; `ReviewsOutboxConfig` holds the application's only `@EnableScheduling` — without it the relay never runs and nothing says so) sends the pending rows oldest first, **waits for the broker's answer** (`get()`, bounded by the producer's `delivery.timeout.ms`), stamps `published_at`, and **stops at the first failure** so one book's events cannot overtake each other. Delivery is **at least once** — a crash between the send and the stamp resends the row — which is why the payload must stay idempotent. **One instance only**: two would send the same rows; claiming them (`FOR UPDATE SKIP LOCKED`) or leader election comes before the reviews service runs replicated. Published rows are kept (no cleanup job yet). Each module that produces events gets its own `<module>_outbox` table while the database is shared. Pinned by `ReviewOutboxAtomicityIntegrationTest` (rollback takes both rows; publish outside a transaction is refused) and `BookRatingEventIntegrationTest`.

**The checkout is an orchestrated saga over Kafka** (step 4 of the microservices migration). `POST /cart/checkout` answers **202** with the order `PENDING` and a `Location`; in one transaction `CheckoutService` claims the cart (`carts.checkout_order_id`, a conditional UPDATE — a second checkout gets **409 `CHECKOUT_IN_PROGRESS`**), saves the order (with its `payment_method`) and writes `ReserveStock` to the orders outbox. From there `CheckoutSagaService` (the orchestrator; the order's status is the saga's state) reacts to replies through `SagaReplyListener`: `StockReserved` → `AWAITING_PAYMENT` + `ChargePayment`; `StockReservationFailed` → `REJECTED` (books in `statusReason`, cart freed); `PaymentApproved` → `CONFIRMED` (cart deleted); `PaymentDeclined` → `PAYMENT_FAILED` + `ReleaseStock` (the compensation, cart kept and freed). A reply in the wrong status is ignored (idempotency by state). Participants: catalog's `StockCommandListener` (→ `ReserveStockForOrderUseCase` — all lines or none, one `stock_reservations` row per order, idempotent by order id, a `FAILED` reservation recorded too, partial takes undone by putting back rather than throwing — and `ReleaseStockForOrderUseCase`) and payments' `PaymentCommandListener`. **Payments never calls the gateway from a listener**: the listener only records the intention (`RequestChargeUseCase` → payment `PENDING`; `RequestRefundUseCase` → `REFUND_PENDING`) with its inbox row, one payment per order; `PaymentGatewayWorker` (`@Scheduled`, 1 s) → `ProcessPendingPaymentsService` calls the gateway **outside** any transaction, then records the answer — and, for a charge, the saga reply via `PaymentReplyPort` → outbox — in one. Every gateway call carries an **idempotency key** (`charge:<orderId>`, `refund:<orderId>`), so calling again after a lost answer (timeout, crash before saving) cannot move money twice. **Any exception from the gateway means "no answer", never a decline**: the payment stays pending, `attempts`/`last_error`/`next_attempt_at` record it, and the wait doubles from `bookland.payments.gateway.retry.initial-delay` (1s) to `max-delay` (1m) with **no last attempt** — giving up on a charge of unknown outcome could leave a customer charged for a failed order. Only the gateway's own refusal of a refund (`RefundRejectedException`) is terminal: `REFUND_FAILED`, for a person to settle. One worker instance only, like the relays. The simulated gateway honours the keys and can be told to fail per customer/order (`failNextCharges`, `failNextRefunds`, `refuseRefunds`) — that is how `PaymentSafetyIntegrationTest` drives outages — or taken down whole from the running app in the **dev profile only**: `PUT /api/v1/admin/dev/payment-gateway/outage {"down": true}` (admin; `GET` shows the state and the charges/refunds actually made). `ProcessPendingPaymentsService.process` returns a `GatewayAttempt` and `PaymentGatewayWorker` logs it — WARN per unanswered call, ERROR per refused refund; before that a gateway outage reached no log at all. Note the backoff's price, measured in 4d: a gateway back after ~70 s down was used only ~55 s later, at the next scheduled attempt. **Topics: the owner of a command topic is its receiver** — catalog owns `bookland.catalog.stock-commands`/`stock-replies`, payments owns `bookland.payments.payment-commands`/`payment-replies`; orders writes their names out rather than importing them. Payloads carry a `messageId` and a `type`; the key is the order id. **Every participating module has its own outbox and its own inbox** (`<module>_outbox`, `<module>_inbox`, copies of the reviews relay — deliberately no shared library) and its own `@EnableScheduling` config; a listener handles each message in one transaction holding the inbox row, the effect and the reply in the outbox. **Cancelling is choreographed, not orchestrated**: only allowed from `CONFIRMED`, it sets `CANCELLED` and writes `OrderCancelled` to the orders outbox in one transaction (`OrderCancellation`, shared by the customer's and the admin's path, through `OrderEventPort`). Orders **owns** `bookland.orders.order-events` (an event's topic belongs to its producer) and expects no answer. Besides `OrderCancelled` it announces `OrderConfirmed`, `OrderPaymentFailed`, `OrderRejected` and `OrderShipped` (step 6a, for the notification service; nothing for `AWAITING_PAYMENT` or `DELIVERED`): **every path that moves an order calls `OrderEvents.announce` after the transition**, in the same transaction — the saga's `advance`, `CancelOrderService`, `UpdateOrderStatusService` — and the event follows from the status reached. All five share one payload (`SagaMessages.OrderEvent`): the order as it stands — `customerId`, `customerEmail`, `customerName`, `status`, `reason`, `totalAmount`, `items`, `occurredAt`. The email and name are **stored on the order at checkout** from the caller's token (`orders.customer_email`/`customer_name`, null on older orders), like the author's name on a review, so no consumer asks the identity service. **A new outbox type must be added to `OrdersOutboxRelay.TOPICS`**: an unmapped one never publishes and, since the relay stops at the first failure, holds back every message behind it. Pinned by `OrderEventsIntegrationTest`. On `OrderCancelled`, catalog's and payments' `OrderCancelledListener`s (bean names prefixed by module — same simple name) release the reservation and refund, each with its inbox, and both effects are idempotent on their own (only a `RESERVED` reservation gives units back; a `REFUNDED` payment is left alone). A refund the gateway does not answer is retried by payments' worker, and one it refuses ends `REFUND_FAILED` — payments' problem, not the order's. Orders no longer depends on bookland-payments in its `pom.xml`. The orders inner layers use their **own** `PaymentMethod`; other modules' types appear only in `infrastructure`, pinned by `other_modules_are_reached_only_through_infrastructure` in orders' `ArchitectureRulesTest`. The simulated gateway declines above `bookland.payments.simulated.decline-above` (default 1000.00). Pinned end to end by `CheckoutSagaIntegrationTest` (approved, declined + compensation, last-copy race, checkout in progress, duplicated commands, customer and admin cancellation, duplicated `OrderCancelled`).

**The notification service emails the customer: Kafka in, RabbitMQ in the middle** (step 6). `bookland-notification-app` runs the `bookland-notification` module alone, with **no web server** (no web starter on the classpath; the process stays up on its listeners) and its own database (`notification`/`notificationdb`, the inbox). `OrderEventListener` (group `bookland-notification`) reads `bookland.orders.order-events`, maps the five types it emails about to `OrderEventKind` and ignores the rest; in one transaction it records the inbox row and calls `NotifyOrderEventUseCase`, which writes the email (`OrderEmailComposer`, domain, plain text; an order with no `customerEmail` gets none) and queues it as an `EmailTask` keyed `<orderId>:<KIND>` through `EmailTaskQueuePort`. **The Kafka offset moves only after RabbitMQ confirmed the task**: `RabbitEmailTaskQueueAdapter` publishes and `waitForConfirmsOrDie` (needs `spring.rabbitmq.publisher-confirm-type: simple`); a failure rolls the inbox row back and the module's Kafka error handler waits it out — exponential 1 s → 30 s for ~5 min, holding the partition — before the dead-letter topic `bookland.orders.order-events.notification.DLT`; each failed try logs a WARN. RabbitMQ is used **only** here, as a task queue: exchange `bookland.notification` (direct) → durable queue `bookland.notification.email`, persistent messages, JSON written by `EmailTaskCodec` with `JsonMapper` (no `__TypeId__`). `EmailTaskListener` sends through `MailSenderPort` → `SmtpMailSenderAdapter` (`JavaMailSender`, SMTP timeouts of 5 s — JavaMail's default is to wait forever). **A failed send waits and tries again, then is set aside** (6c): `EmailTaskListener` catches the mail server's failure, sends a copy marked `x-bookland-attempt`/`x-bookland-last-error` to a **wait queue** — one per delay of `bookland.notification.retry.delays` (10 s, 1 min, 5 min: four tries in all), each with that TTL on the queue and a dead-letter route (`email`) back to the email queue — through `EmailTaskRedelivery` (confirmed, like the first publish) and **then** acknowledges the original; after the last delay the copy goes to `bookland.notification.email.dlq` (WARN per failed try with the next delay, ERROR when given up). The TTL is per queue, not per message, because the broker expires only the message at the head of a queue. What the listener cannot handle that way — a body that is not a task, a retry the broker refuses — is thrown; its own `notificationRabbitListenerContainerFactory` rejects it **without requeue** (the default would hand it back at once, forever), and the email queue's own dead-letter route takes it to the same DLQ: nothing is dropped, nothing reprocesses the DLQ automatically. **One email per order and kind**: `SendEmailService` checks `sent_emails` by the task's key before sending and records it after — so a task queued twice (inbox committed after a crash) or retried after a send that went through is dropped; a crash between the send and the record sends once more, the accepted gap. **A queue's arguments cannot change once it exists** (`PRECONDITION_FAILED`, 406 — measured in 6c, when the old container redeclared the queue first): changing the topology means stopping the service and deleting the queue on the broker. Dependencies the web starter used to bring: `spring-boot-starter-jackson` (Jackson 3 and the `JsonMapper` bean). Tests replace RabbitMQ and SMTP at their ports (`NotificationTestDoubles`: an in-memory queue that runs the real codec and listener, a recording mail sender) and keep the RabbitMQ container stopped (`spring.rabbitmq.listener.simple.auto-startup=false` in `@NotificationIntegrationTest`); the real broker is exercised end to end. Pinned by `OrderEventNotificationIntegrationTest`.

**Modules read the catalog over gRPC, not in memory** (step 5: block 5a introduced it inside the monolith; since 5b the catalog runs as **`bookland-catalog-app`**, catalog + inventory with their own database `catalog`/`catalogdb`, its own consolidated migration `V20261007130000__catalog_schema.sql`, the monolith's `V20261007140000__drop_catalog_tables.sql` dropping them here, the dev book seed moved along, and the same Kafka consumer groups so offsets carry over). The monolith's `catalog` channel points at the catalog service (`static://localhost:9091` in dev, `CATALOG_GRPC_ADDRESS` in compose); the catalog's `orders` channel at the monolith (`static://localhost:9090`, `ORDERS_GRPC_ADDRESS`). **Monolith tests no longer have a catalog**: `FakeCatalog` (test configuration imported by `@BooklandIntegrationTest`) serves `BookCatalog` over the in-memory gRPC and plays the saga participant on Kafka (reserve all-or-nothing, release, `OrderCancelled`), with in-memory books each test creates (`addBook`, `stock`, `reservationStatus`); the real catalog's side is tested in bookland-catalog-app (`@CatalogIntegrationTest`, with `FakeOrderActivity` answering `HasActiveOrders`). Spring gRPC 1.0.x (the line for Boot 4.0.x) with **`grpc-netty-shaded`** in place of `grpc-netty` (its own Netty, out of reach of Boot's Netty version). The catalog **owns** `bookland/catalog/v1/book_catalog.proto` (`BookCatalog.GetBooks`, a **batch** — a cart is one call — unknown/removed books simply absent, price as decimal text); orders owns `bookland/orders/v1/order_activity.proto` (`HasActiveOrders`, asked by the catalog before removing a book — orders used to implement the catalog's port in process). **Consumers keep a copy** of the owner's file in their `src/main/protobuf` that may differ **only in `java_package`** (so generated classes do not collide on the shared classpath); `GrpcContractCopiesTest` (bookland-app) fails on any other difference — the copy is compiled, so drift is otherwise silent until the wire disagrees. Code is generated by `io.github.ascopes:protobuf-maven-plugin` (versions in the parent pom must match the Spring gRPC BOM). Servers are `BindableService` beans in `infrastructure/grpc` (`BookCatalogGrpcService`, `OrderActivityGrpcService`); clients are the port adapters there too (`CatalogGrpcBookInfoAdapter`, `CatalogGrpcWishlistBookInfoAdapter`, `CatalogGrpcBookExistsAdapter`, `OrderActivityGrpcAdapter`), each with a **deadline** (`bookland.grpc.*.deadline`, 2s) and, for the catalog readers, its own Resilience4j **circuit breaker** (core library, built in code; state changes logged). Any failure becomes the module's own `CatalogUnavailableException`/`OrdersUnavailableException` → **503** `CATALOG_UNAVAILABLE`/`ORDERS_UNAVAILABLE`; reading the cart or wishlist degrades every item to "Unavailable" instead, and the checkout refuses. "Not found" is each module's own `BookNotFoundException` (same `BOOK_NOT_FOUND`). orders, wishlist and reviews have **no Maven dependency on bookland-catalog**; `CatalogBoundaryRulesTest` (ArchUnit) forbids any catalog/inventory import outside them. Channels `catalog`/`orders` in `spring.grpc.client.channels.*` (`static://localhost:9090`; env `CATALOG_GRPC_ADDRESS`, `ORDERS_GRPC_ADDRESS`), server on `GRPC_PORT` (9090), **not published** by compose. **No authentication between services** (decision); Spring gRPC's three `security` autoconfigurations are excluded in `application.yml` — `OAuth2ResourceServerAutoConfiguration` otherwise activates on web-support's Spring Security classes and fails the context on a Boot properties class we do not have. Integration tests run gRPC **in process** (`spring.grpc.test.inprocess.enabled` in `@BooklandIntegrationTest`, `spring-grpc-test`): no port, every channel reaches the in-memory server. The monolith's Dockerfile builds on `eclipse-temurin:21-jdk` (glibc), not alpine: `protoc-gen-grpc-java` does not run on musl.

**Soft-deleted books are invisible outside the catalog.** `GetBookByIdUseCase` and `GetBooksByIdsUseCase` (the batch served over gRPC) filter out inactive books, so a removed book cannot be fetched (404), added to a cart/wishlist (404) or checked out (409 `CartItemUnavailableException`, via `BookInfoPort.findBookInfo` returning empty). Admin write flows (update / cover upload / removal) bypass it and go straight to `BookPersistencePort.findById`, which still sees inactive books. `available` on a `BookViewModel` means `active && stockQuantity > 0`.

**Bean names must be unique across modules.** Adapters duplicated per module with the same simple class name (e.g. `TransactionAdapter` in wishlist and orders) collide under component scanning — give the later one an explicit name: `@Component("ordersTransactionAdapter")`.

**Transactions are framework-free** via `TransactionPort` (outbound port, `inTransaction(Supplier<T>)`) implemented in infrastructure with `TransactionTemplate`. Do **not** put `@Transactional` on application services (breaks framework-freedom and does not work without a Spring proxy under manual wiring). No-rollback semantics (e.g. checkout must commit the `PAYMENT_FAILED` order on a declined payment) are expressed by **returning** an outcome from the transaction and throwing the exception after the commit — see `CheckoutService`.

**Pagination is framework-free** via `PageQuery`(page, size) and `PageResult<T>` in each module's `application/common/` (deliberately duplicated per module — no shared kernel). Persistence adapters translate `PageQuery ↔ PageRequest` and `Page ↔ PageResult`; fixed sort orders live in the adapter. `PageResult<ViewModel>` is also the paged HTTP response envelope (content/page/size/totalElements/totalPages).

**Port/Adapter pattern for all I/O:** persistence, password encoding, JWT generation, transactions, cross-module lookup and image storage are all accessed through interfaces in `application/port/out/`; infrastructure adapters implement them. Cover images are stored via `ImageStoragePort` (catalog out-port) — the `LocalImageStorageAdapter` writes bytes to `bookland.storage.covers-location` and returns a public `/media/covers/...` path served by `MediaResourceConfig`; swap in an S3/GCS adapter without touching inner layers. `MultipartFile` never crosses the web layer: `BookApiController` extracts `byte[]` + filename + contentType into a framework-free `UploadBookCoverCommand`.

### Auth Flow

`bookland-auth` **hosts a Spring Authorization Server** (OAuth2 + OIDC) and every other module is a Resource Server validating the tokens it issues. Since step 3 of the microservices migration auth runs with user as **the identity service** (`bookland-identity-app`, port 9000, its own database with `users` and the `oauth2_*` tables); the monolith validates its tokens against the public keys fetched from `/oauth2/jwks` and holds no user data (`V20261006130000` dropped those tables). No BFF. Login is `authorization_code` + PKCE: the browser goes to `/oauth2/authorize`, authenticates against `BooklandUserDetailsService` (→ `UserLookupPort` → user module) through Spring's own `DaoAuthenticationProvider`, and the client exchanges the code at `/oauth2/token` for an access token, an `id_token` and a refresh token. Refreshing is `grant_type=refresh_token` at the same endpoint, single-use; ending a session is `/connect/logout`. **There is no `/api/v1/auth/login`, `/refresh` or `/logout`** — those were a hand-written implementation of the above and were deleted.

`POST /api/v1/auth/register` survives, because registering is business logic and not authentication: e-mail uniqueness, the default CUSTOMER role and the invariants of `User.create` have nowhere to live inside a protocol endpoint. It answers **201 with the account** (`id`, `email`, `name`, `role`) and **no credential**, and establishes the Authorization Server's session (`RegistrationSessionEstablisher`) so the client can go straight to `/oauth2/authorize` without a second password prompt. There is no user-creation endpoint in the user module itself.

**`sub` carries the internal `UserId`, never the e-mail** — written by `BooklandTokenCustomizer` into *both* tokens, with no filter by token type, alongside `email`, `role` and `name` (the display name; on a refresh, `role` and `name` are re-read from the account). This is not a preference: OIDC requires `sub` to be stable and never reassigned, every business column stores the `UserId`, and after the old filter's removal `sub` is the only channel identity travels through. The customizer reads the id from `BooklandUserDetails`, a custom `UserDetails` that exists because the framework's interface has nowhere to put an id. Two consequences that are easy to get wrong and are documented at length in `docs/oauth2-customizations.md`: a custom principal must be added to the polymorphic-typing allowlist (`AuthorizationJsonMapperFactory` + `BooklandUserDetailsMixin`) or the code exchange 500s, and it must implement `CredentialsContainer` or the BCrypt hash is written into `oauth2_authorization.attributes`.

**The access token carries `aud = bookland-api`; the `id_token` keeps the client id.** Both halves are required: the generator gives both tokens the same `aud` by default and the default decoder validates none, so without `BooklandTokenCustomizer` *and* `ApiAudienceValidator` an `id_token` works as a Bearer credential at the API. Pinned by `AuthorizationCodeFlowIntegrationTest`.

Signing is **RS256 with an RSA pair read from `bookland.oauth2.jwk.*`** (base64 DER, single-line so it fits an env var), published at `/oauth2/jwks`. The private half never leaves the signing path — unlike the HMAC secret it replaced, which let every component able to *validate* a token also *mint* one.

**Four `SecurityFilterChain`s, and the order is load-bearing** — 1 and 2 in `bookland-auth` (`AuthorizationServerConfig`), 3 and 4 in `bookland-web-support` (`ApiSecurityConfig`), so any process with web-support serves its API as a resource server whether or not it hosts the Authorization Server. The identity service runs all four; the monolith runs only 3 and 4. Chain 1 also claims `OPTIONS /oauth2/token`: the configurer matches its token endpoint as `POST` only, so without that the CORS preflight fell through to chain 4 and got a 401:

| Order | Matches | Session | Purpose |
|---|---|---|---|
| 1 | the configurer's own endpoint matcher (`/oauth2/*`, `/userinfo`, discovery) | stateful | the Authorization Server; also a resource server, because `/userinfo` is itself token-protected |
| 2 | `/login`, `/login/**` | stateful | the form login (Spring's generated page for now) |
| 3 | `/error`, `/media/**`, `/h2-console/**`, swagger, `/api-docs/**` | stateless | **no resource server** — see below |
| 4 | everything else | stateless | the API, as a resource server |

Chain 3 exists because the resource server rejects an unusable Bearer token *wherever* it appears, while the filter it replaced recorded the reason and carried on. On the `ERROR` dispatch that turns a real 500 into a 401, which is the disguised-session bug this project already fixed once. `/api/v1/books` and `/api/v1/categories` are deliberately **not** in chain 3: their public reads share a path prefix with admin writes, and a chain claiming them by path would have to reproduce the method-by-method rules to avoid opening a write route.

**Each module declares its own access rules** as an `AuthorizationRules` bean (contract in bookland-web-support) in its `infrastructure/config` — `AuthAuthorizationRules`, `CatalogAuthorizationRules`, `InventoryAuthorizationRules`, `ReviewsAuthorizationRules` — listing only its departures from the default: public routes, and admin routes outside `/api/v1/admin`. Chain 4 (`ApiSecurityConfig`) owns no route-specific rule: it applies every module's rules, then the default (`/api/v1/admin/**` → ADMIN, then `anyRequest().authenticated()`). **Rules from different modules must never be able to match the same request**, because the order the beans are collected in is undefined: under the shared `/api/v1/books` prefix each module writes `/api/v1/books/*` plus its own suffix, never `/api/v1/books/**` (that wildcard is how review moderation used to be admin-only only through the catalog's `DELETE /api/v1/books/**`). **`AccessMatrixIntegrationTest`** (one per application, each over its own routes) pins who may call every route (no token / CUSTOMER / ADMIN) and reads the routes from Spring MVC, so a new endpoint without a row in the matrix fails the build. `JwtAuthenticationConverter` maps the `role` claim to a `ROLE_*` authority — without it every token is valid, every caller is authenticated and carries no authority at all, so every admin route answers 403 including to an admin.

**A handler that needs to know who is calling declares an `AuthenticatedUser` parameter** — never `Principal`, and never `SecurityContextHolder` directly. `AuthenticatedUserArgumentResolver` (bookland-web-support, registered by `AuthenticatedUserConfig`) is the single place that knows how identity rides on the `Authentication`, which is precisely what changes if the authentication mechanism does (OAuth2 resource server: a claim read; external IdP: a lookup from the issuer's `sub`). It **never returns null** — no caller is an `AuthenticationCredentialsNotFoundException` that `ExceptionTranslationFilter` renders as the contract's 401, and an authentication carrying no UUID is an `IllegalStateException`, i.e. the 500 a wiring bug deserves. The predecessor was an `instanceof` over `getDetails()` copy-pasted into six controllers that returned `null` on mismatch, so a filter change would have silently attributed carts and orders to a null customer instead of failing. **`AuthenticatedUser` must stay registered in `OpenApiConfig`'s `SpringDocUtils.addRequestWrapperToIgnore`** — to springdoc an unannotated POJO parameter is a set of query parameters, and without it the document publishes `caller` as a *required* query param on every such operation. Pinned by `AuthenticatedUserArgumentResolverTest` and `OpenApiErrorContractIntegrationTest`.

**401 and 403 are distinct and must stay that way** — see `docs/error-contract.md`, which is the contract clients code against. A missing/expired/invalid token is **401** (`TOKEN_MISSING` / `TOKEN_EXPIRED` / `TOKEN_INVALID`); an authenticated caller without the role is **403** (`INSUFFICIENT_ROLE`). Both are `application/problem+json` with a machine-readable `code`. This only works because `ApiSecurityConfig` wires `.exceptionHandling(...)`: without it Spring Security falls back to `Http403ForbiddenEntryPoint` and answers *everything* with an empty 403, which is indistinguishable to a client. `RestAuthenticationEntryPoint` renders the body from a reason recorded under `AuthErrorCode.REQUEST_ATTRIBUTE`; what records it is now `BearerTokenErrorClassifier`, which wraps that entry point and reads the cause out of the exception chain — and it must be registered **inside** `.oauth2ResourceServer(...)` as well as in `.exceptionHandling(...)`, because the resource server installs its own entry point that answers with an empty body. `TOKEN_EXPIRED` is told apart from `TOKEN_INVALID` by `AccessTokenExpiryValidator`, which exists solely to fail expiry under an error code of our own: the framework's `JwtTimestampValidator` reports it as `invalid_token` like everything else, leaving an English message as the only discriminator. **A rejected token on a public endpoint now *does* fail the request** — `GET /api/v1/books` with an expired token answers 401. `AuthErrorContractIntegrationTest` (bookland-app) locks all of this against the real filter chain.

Public endpoints: `POST /api/v1/auth/register`, `/oauth2/**`, `/login`, `/.well-known/**`, `GET /api/v1/books/**`, `GET /api/v1/categories/**`, `GET /media/**` (stored cover images), `/error`, `/h2-console/**`, `/swagger-ui/**`, `/api-docs/**`.

**`/error` must stay `permitAll`.** Boot registers the security chain for the `ERROR` dispatch too, so when an unhandled exception makes the container forward to `/error`, an authenticated `/error` answers the *forward* with `401 TOKEN_MISSING` — the real 500 never reaches the client, and arrives disguised as an expired session that makes clients refresh and then log the user out. `ProblemDetailErrorController` (bookland-web-support) renders that dispatch as problem+json with `code: INTERNAL_ERROR` and `instance` set to the **original** request path; a 5xx never echoes the exception message (stack traces, SQL, column names). Pinned by `ProblemDetailErrorControllerTest` and `BusinessErrorContractIntegrationTest`. Admin-only (`ROLE_ADMIN`): book/inventory writes including cover upload (`POST /api/v1/books/{id}/cover`, `multipart/form-data`, part `file`), `/api/v1/admin/**` — which includes the order back-office: `GET /api/v1/admin/orders?status=&page=&size=` (all orders, newest first, `AdminOrderSummaryViewModel` rows carrying `customerId`), `GET /api/v1/admin/orders/{id}`, `GET /api/v1/admin/orders/customer/{customerId}` and `PATCH /api/v1/admin/orders/{id}/status`. Everything else requires authentication.

### Technology Notes

- **Java 21**, Spring Boot 4.0.6
- **MapStruct** for all struct-to-struct mapping (configured with `defaultComponentModel=spring`; Lombok binding order matters — Lombok processor must come before MapStruct in `annotationProcessorPaths`)
- **H2** in dev (`spring.profiles.active=dev`), **PostgreSQL 16** in prod. Both JDBC drivers are declared in each application (`bookland-app`, `bookland-identity-app`, `bookland-catalog-app`, `bookland-notification-app`), not in a domain module. Each application has its **own database** (`booklanddb`/`identitydb`/`catalogdb`/`notificationdb` in dev; databases `bookland`/`identity`/`catalog`/`notification` in prod)
- **Flyway owns the schema in both profiles**, and `ddl-auto` is `validate` in both (Flyway creates, Hibernate verifies the mapping and refuses to boot on a drift). Migrations live in each application's `src/main/resources/db/migration` (the identity service started from a consolidated `V20261006120000__identity_schema.sql`), versioned by **timestamp** (`V20260726164500__init_schema.sql`) so parallel branches cannot collide. Dev runs the same migrations against H2 opened with `MODE=PostgreSQL` — so **migration SQL must stay in the PostgreSQL/H2 common subset**, and a migration that breaks fails on the next dev boot rather than in prod. There is no `import.sql`; the categories are reference data in `V2`. **Boot 4 gotcha:** `flyway-core` alone does nothing — the auto-configuration lives in `spring-boot-flyway`, so the dependency must be `spring-boot-starter-flyway` (plus `flyway-database-postgresql`; H2 support is inside `flyway-core`). Without it Flyway fails silently: no error, no migrations applied
- **`AdminBootstrap`, `DevCustomerSeeder` and `DevDataLoader` must all stay idempotent** — they look up before inserting (`GetUserByEmailUseCase`; `IsbnAlreadyExistsException` per book). The in-memory H2 survives a devtools restart (`DB_CLOSE_DELAY=-1`) and Flyway no longer wipes it as `create-drop` did, so a non-idempotent seed breaks the second start. The category UUIDs in `V2` are referenced literally by `DevDataLoader`'s constants — changing them breaks the book seed
- **H2 console** needs `spring-boot-h2console` (bookland-app, runtime) — the third case of the same Boot 4 gotcha: without it `spring.h2.console.enabled` is ignored and `/h2-console` answers 404, silently. Pinned by `BooklandApplicationTests`
- **Kafka** (`spring-boot-starter-kafka` in the producing/consuming modules; bootstrap servers `${KAFKA_BOOTSTRAP_SERVERS:localhost:9092}`). Same Boot 4 gotcha as Flyway: the auto-configuration lives in `spring-boot-kafka`, so plain `spring-kafka` compiles but creates no `KafkaTemplate` and no listener container — it must be the starter
- **Datasource URL is `${DB_URL:jdbc:postgresql://localhost:5432/bookland}`.** `docker-compose.yml` injects `DB_URL` pointing at the `postgres` service name; the default covers running the app from the host against the compose Postgres (port 5432 is published)
- **FKs exist only within a module.** Cross-module columns (`cart_items.book_id`, `orders.customer_id`, `payments.order_id`, …) are indexed `uuid` with no constraint, mirroring the absence of cross-module JPA relationships. Do not add them without discussing the module-split implications
- **Spring Authorization Server** (via `spring-boot-starter-security-oauth2-authorization-server`, versionless — it inherits `spring-security.version`). Issuer, RSA key pair, API audience and the one registered client are configured under `bookland.oauth2.*`; Flyway creates the three `oauth2_*` tables and `ClientBootstrap` writes the client row, idempotently. **Do not add JJWT back** — nothing signs tokens by hand any more
- **Admin bootstrap**: `AdminBootstrap` (bookland-user `infrastructure/bootstrap`, `@Order(1)`, all profiles) guarantees exactly one admin user on startup — credentials under `bookland.admin.email/password` (prod: `ADMIN_EMAIL`/`ADMIN_PASSWORD` env vars). The dev seeds are split by owner: `DevCustomerSeeder` (bookland-user, dev only) seeds the sample customer, `DevDataLoader` (bookland-catalog `infrastructure/bootstrap`, dev only) seeds the books. The seeds live with the module they use, so they travel with it when it is extracted
- **Nothing outside user/auth may depend on them** — `IdentityBoundaryRulesTest` (ArchUnit, bookland-app) fails the build otherwise. They become the identity service; every other module learns who the caller is from the access token (`AuthenticatedUser`: `id`, `email`, `name`), never by calling the user module
- **Cover image storage**: local filesystem in dev/single-node. Location under `bookland.storage.covers-location` (dev: `./bookland-data/covers`; prod: `STORAGE_COVERS_LOCATION` env, default `/var/bookland/covers` — mount a volume so uploads survive restarts). Upload limits under `spring.servlet.multipart.*` (5 MB); allowed types JPEG/PNG/WEBP validated in `UploadBookCoverService`
- **ArchUnit** (`archunit-junit5`, test scope) enforces framework-freedom of the inner layers and the inward dependency direction — one `ArchitectureRulesTest` per domain module
- **Tests** are plain JUnit 5 + Mockito + AssertJ unit tests against mocked ports (`TransactionPort` is faked with a pass-through, not mocked); `BooklandApplicationTests` (bookland-app) and `IdentityApplicationTests` (bookland-identity-app) boot the full contexts and validate all composition-root wiring. **Every full-context test is annotated `@BooklandIntegrationTest`** (`@SpringBootTest` + MockMvc + `dev` profile + `@EmbeddedKafka` + the test signing key) — or `@IdentityIntegrationTest` in the identity service, which has no Kafka, or `@CatalogIntegrationTest` in the catalog service — never with those annotations spelled out: the context starts a Kafka listener and producer and needs a broker, and one identical configuration keeps the whole suite on a single cached context and a single in-JVM broker. Asynchronous effects (an event's consumer) are awaited with Awaitility, never `Thread.sleep`. There are no `@WebMvcTest` slices
